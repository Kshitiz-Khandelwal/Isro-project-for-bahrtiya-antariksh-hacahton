Phase 9 — Risk Analysis

R1: FRR MPLS configuration complexityProbability: High · Impact: High

Getting LDP-based MPLS forwarding working with BGP and OSPF in FRR containers is non-trivial. A misconfigured MTU or wrong LDP neighbor causes silent failures that are hard to debug.

Mitigation: Start with a minimal 2-node topology and get MPLS ping working before adding more nodes. Have a pre-tested config YAML ready before the hackathon. Fallback: drop MPLS, do pure BGP + OSPF if LDP fails — most of your monitoring still works.
R2: LLM hallucination under pressureProbability: High · Impact: High (35% score)

Without structured output enforcement and a carefully designed system prompt, the LLM will produce correct-sounding but wrong responses when judges ask unexpected questions live.

Mitigation: Use Ollama's JSON format mode. Pre-test 20+ questions across all 4 scenarios before submission. Define a system prompt that explicitly instructs the model to say "I don't have sufficient information" rather than hallucinate. Validate every response against the JSON schema.
R3: Insufficient training dataProbability: Medium · Impact: High

2 hours of fault injection may not produce a robust classifier. The model could overfit to specific fault injection patterns.

Mitigation: Run all 4 fault scenarios simultaneously across different interfaces. Use data augmentation (Gaussian noise). Rely on Prophet (which doesn't need classification labels) for your primary time-to-impact claim. Have a pre-generated synthetic dataset as backup.
R4: Resource constraints on demo machineProbability: Medium · Impact: High

Running all components simultaneously (~14 GB RAM) on a laptop risks swapping, which will make the LLM response time unacceptably slow during demos.

Mitigation: Use Phi-4-mini (3.8B, ~2.5 GB) if RAM is tight. Pre-load the model before the demo presentation starts. Close all other applications. Consider splitting components across two machines if available.
R5: Scenario 4 (controller misconfiguration) is harder than it looksProbability: High · Impact: Medium

Detecting QoS policy drift through traffic pattern anomalies requires that your traffic generator is marking QoS correctly AND that your monitoring captures DSCP values. This is significantly harder than the other 3 scenarios.

Mitigation: Simplify Scenario 4 — instead of QoS drift, demonstrate it as a route leak or policy change that causes unexpected traffic path (detectable via BGP-MIB and flow records). Or use a manual Isolation Forest alert on an anomalous traffic distribution pattern.
R6: Windows development environmentProbability: Medium · Impact: Medium

The file paths in your roadmap suggest Windows. Containerlab requires Linux. WSL2 works but adds complexity, and performance for Docker networking in WSL2 can be unpredictable.

Mitigation: Do all Containerlab work on a Linux machine or a Linux VM. Use WSL2 only if a Linux machine is unavailable, and test it thoroughly before hackathon day.

Phase 10 — Missing Opportunities

Opp 1: Structured LLM output with JSON schema enforcementCritical · Low effort · Very high impact

This is the highest-ROI change you can make. The PS explicitly lists the required structured output fields. Using Ollama's format: "json" and a system prompt with a JSON schema template guarantees consistent, parseable, displayable copilot responses. Without this, the 35% copilot score is largely at the mercy of probabilistic generation.

Implementation effort: Low (2-3 hrs) · Expected score impact: +8-12 points on copilot dimension

Opp 2: Air-gap verification scriptCritical · Low effort · High impact

A small Python script that attempts to reach external IPs and DNS and shows "BLOCKED — all inference is local" on the dashboard. Run it live during the demo. This turns an unverifiable claim into a demonstrable feature and directly addresses the 20% security dimension.

Implementation effort: Low (1 hr) · Expected score impact: +4-6 points on security dimension

Opp 3: Graph-based scope determination in copilot responsesRequired by Obj 4 · Medium effort · High impact

When the LLM says "affected scope: Branch-2 and Branch-3," it needs to be factually derived from topology traversal, not guessed. Build a simple NetworkX graph from your Containerlab topology YAML. On each alert, run a BFS/DFS from the affected device to find all downstream sites. Inject the result as: "Devices on affected path: CE-Branch2, CE-Branch3. VPN services impacted: VRF-CORP, VRF-MGMT."

Implementation effort: Medium (3-4 hrs) · Expected score impact: +5-8 points across technical + copilot dimensions

Opp 4: Pre-recorded fallback demoInsurance · Low effort · Essential

Record a clean 5-minute screen capture of your working system running all 4 validation scenarios. If anything breaks during the live demo, you have evidence to fall back on. Many hackathon submissions fail at the demo stage despite a working system — this is pure risk mitigation.

Implementation effort: Low (1 hr) · Expected impact: Prevents catastrophic score loss

Opp 6: softflowd for NetFlow/IPFIX (required dataset)PS requirement · Low effort
